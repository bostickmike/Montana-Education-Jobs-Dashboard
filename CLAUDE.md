# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An R-based, weekly-updated Shiny dashboard of K-12 and higher-ed job openings in Montana, with salary/staffing/Census context. It's a port of the [Wyoming Education Jobs Dashboard](https://github.com/bostickmike/Wyoming-Education-Jobs-Dashboard) — much of the state-agnostic logic (classification, drift checks, history accumulation) was ported near-verbatim, while scraping targets and state-specific data sources were rebuilt for Montana. `RESEARCH_NOTES.md` documents the scoping research (district counts, ATS platform landscape, salary-source gaps) that shaped every structural decision in the port, and is worth reading before assuming Montana's data model mirrors Wyoming's.

**Shared code lives in the `edjobs` package** ([bostickmike/edjobs](https://github.com/bostickmike/edjobs); migration plan in the workspace's `claude-notes/2026-11-10_r-package-migration-plan.md`). This repo pins a tagged version in `EDJOBS_VERSION`; every workflow that runs the tests installs it (`weekly-scrape.yml`, and `.github/actions/setup-r-env` for the PR, Copilot and Claude auto-fix workflows). Locally: `pak::pak(paste0("bostickmike/edjobs@v", readLines("EDJOBS_VERSION")))`, or `devtools::load_all("../edjobs")` while changing the package. `test-run-expectations.R` fails if the installed version isn't the pinned one. A function that has moved to the package is deleted here in the same change: a local copy would mask the package's. Bump `EDJOBS_VERSION` only after the package's tag passes its own check and a full rehearsal; the weekly run doesn't gate a bump (when unsure, test-dispatch the weekly workflow on a branch copy and discard its data). In the package since phase 2 (2026-11-11): the classifier and posted pay, IPEDS staff salaries, the shared drift/data-quality/auto-fix helpers, `check_file_schema()`, `check_total_matches_parts()`, `rebuild_parity_row()`; this repo's `k12_he_classification.R`, `drift_check.R`, `schema_check.R` and `history_accumulator.R` keep the state's own parts and attach edjobs. Phase 3 (2026-11-11, edjobs 0.5.0) moved the shared platform code (AppliTrack fetch/parse, SchoolSpring details and ending reasons, PeopleAdmin page pay and dates, NEOGOV card pay); `direct_api_scrapers.R` attaches edjobs. A scraper-autofix issue whose fetch function is an edjobs export gets a companion issue on edjobs, assigned to Copilot there (`COPILOT_TOKEN` covers edjobs); if it's still flagged later, the Claude fallback runs from this repo with edjobs checked out at the pinned tag in `.edjobs/` and opens its fix PR on edjobs. After an edjobs fix merges: tag, and bump `EDJOBS_VERSION` in both states.

## Commands

Install dependencies (no lockfile/package manager — plain `install.packages`):

```r
install.packages(c(
  "rmarkdown", "dplyr", "purrr", "readr", "readxl", "rvest",
  "stringr", "tidyverse", "writexl", "xml2", "jsonlite",
  "httr2", "lubridate", "chromote", "rsconnect", "testthat",
  "withr", "here", "pdftools", "tibble",
  "shiny", "bslib", "shinyWidgets", "DT", "data.table",
  "leaflet", "plotly", "scales", "shinycssloaders"
))
```

Run the dashboard against data already committed in the repo (no scraping):

```r
shiny::runApp("Mt_Ed_Jobs")
```

Run the full scrape/build pipeline (hits every live source; needs a real headless Chrome for the Apptegy/CyberSchool scrapers — set `CHROMOTE_CHROME` if not auto-detected; needs `CENSUS_API_KEY` in `.Renviron` for the Census ACS/SAIPE chunk, everything else runs without it):

```r
rmarkdown::render("Mt_ED_Jobs.Rmd")
```

Run the full test suite:

```r
testthat::test_dir("tests/testthat")
```

Run a single test file:

```r
testthat::test_file("tests/testthat/test-k12-posting-identity.R")
```

Rebuild accumulated K-12/HE history from the committed raw archives from scratch (disaster recovery, or to verify the incremental accumulator path hasn't drifted from a full rebuild):

```r
Rscript scripts/rebuild_k12_history_from_archive.R
Rscript scripts/rebuild_he_history_from_archive.R
```

The rebuild reproduces the committed files exactly (`Rscript .github/scripts/check_rebuild_parity.R`, also a non-blocking weekly step): K-12 rows go through the same `read_counted_archive_week()` (`opi_reconcile.R`, one archive file at a time) and `build_k12_combinedclean()` / `build_k12_teacher_rows()` (`history_accumulator.R`) as the pipeline. The classifier lives in edjobs (`R/k12_he_classification.R`) since phase 2 (2026-11-11). After changing it there (or this repo's `k12_he_classification.R`, which keeps only the state's name corrections and posting identity), reclassify the committed data with `Rscript scripts/reclassify_committed_data.R --edjobs ../edjobs` (dry run; `--apply` writes, after `R CMD INSTALL ../edjobs`; it compares the pinned tag with the edjobs checkout): `test-weekly-data-quality.R` fails until every committed bucket equals what the classifier gives its title (and the posting spells' `Position`). Review a classifier change with `Rscript scripts/classifier_archive_diff.R --edjobs ../edjobs` (pinned tag vs. checkout; add `--also ../<sibling repo>` for both states' archives): it lists every archived title whose bucket moves, and every line should be intended; the reclassify script prints it too. A bare word in a pattern matches inside other words ("Aide" in "Raiders", "Para" in "Paradise"): anchor with `\b`, and add a golden-set guard row.

## Architecture

**Pipeline vs. dashboard are separate R programs sharing derived CSVs.** `Mt_ED_Jobs.Rmd` is the single pipeline entry point — it scrapes every source, classifies/cleans postings, and appends this week's newly derived rows onto the accumulated datasets in `Mt_Ed_Jobs/`. `Mt_Ed_Jobs/app.R` is the Shiny dashboard that reads those same committed CSVs; it never scrapes anything itself. The weekly GitHub Actions workflow (`.github/workflows/weekly-scrape.yml`) runs the pipeline, and a commit+push of the changed CSVs is what triggers the Posit Connect Cloud redeploy of the dashboard — there is no build step connecting the two beyond that shared data.

**Scrapers are split by reliability, not by K-12/HE.** `direct_api_scrapers.R` holds scrapers against real platform APIs (AppliTrack, SchoolSpring, TedK12, Tyler Portico, Paycom, JazzHR, NEOGOV, ADP Workforce Now, isolved Hire, OPI's statewide feed) — both K-12 and HE. `misc_district_scrapers.R` / `misc_college_scrapers.R` hold heuristic scrapers (including the `chromote`-driven Apptegy/CyberSchool ones needing a real headless browser) for districts/institutions with no structured ATS, kept deliberately separate since they're a real but acknowledged-less-reliable source. `k12_district_registry.csv` / `he_institution_registry.csv` are the hand-maintained lists of every directly-scraped target, its platform, and its feed/job-board URL — adding a district or institution means adding a registry row plus (usually) a scraper.

**`llm_extract_scraper.R` is a third, quarantined scraper tier — a shadow pilot.** For district employment pages that publish openings as free-text prose with no structural marker a hand-written parser can key on (Grass Range, Rapelje — the "declined: unstructured prose" tail of the OPI-coverage work), it renders the page with `chromote`, sends `document.body.innerText` to the Google Gemini API (OpenAI-compatible endpoint, `GEMINI_API_KEY` free tier — GitHub Models was the original target but was retired 2026-07-30) with a JSON schema, then applies deterministic guardrails (every returned title must literally appear on the page; an implausible count drops the whole result; boilerplate is filtered). It is **not** wired into the K-12 combine: `fetch_all_llm_extracted_postings()` writes only `Mt_Ed_Jobs/llm_extract_shadow.csv`, pilot districts are **not** in `k12_district_registry.csv`, and nothing it produces touches the dashboard or the sanity/schema/drift checks. Targets live in `llm_extract_targets.csv`; the full lifecycle (add → watch the shadow file for weeks → promote by hand) is in `LLM_EXTRACT.md`. The one non-deterministic piece (`llm_extract_call()`) is isolated and swappable; `tests/testthat/test-llm-extract-scraper.R` covers the guardrails against a real captured fixture without a network call.

**Classification is centralized and shared.** The `classify_*` functions (position, subject, broad category, HE job type/faculty category), title repair and posted pay live in the edjobs package (phase 2, 2026-11-11); this repo's `k12_he_classification.R` keeps the district/institution name canonicalization and posting identity and attaches edjobs, and is sourced by both the K-12 and HE munge chunks in the pipeline and by any one-off rebuild script — this is deliberate, so "what the pipeline produces next run" and "what a rebuild-from-archive script produces now" can never silently diverge. `scrape_helpers.R` and `schema_check.R` (whose `REQUIRED_SCHEMAS` is enforced against real committed data by `tests/testthat/test-schema-check.R`) are sourced the same way.

**Accumulation, not rebuilding.** `history_accumulator.R`'s `append_weekly_rows()` takes only this week's freshly classified rows and appends them onto the existing accumulated CSV (idempotent — a same-day re-run replaces that day's rows rather than duplicating them), instead of reprocessing the full raw archive every run. `Archivek12_Data/` / `Archived_HE_Data/` still get one dated raw snapshot per week as the durable source of truth; the `scripts/rebuild_*_history_from_archive.R` scripts exist specifically to regenerate accumulated data from those archives when the incremental path needs to be checked or disaster-recovered.

**Posting identity is a specific contract, not just a dedup step** (`DATA_COOKBOOK.md`, "Posting identity"). A `Posting_ID` is assigned once, before any current count, vacancy numerator, weekly total, longitudinal aggregate, trend, or New This Week comparison. Structured sources use a real stable per-posting URL when available; a listing/board URL is never mistaken for one, since a single board holds many posts. Sources with no stable ID (including OPI, whose fallback uses title + raw location + posted date) get an explicit fallback tracked in `Posting_Identity_Method`, with a count-preserving occurrence suffix on equal fallback rows rather than silent deduplication. Any change touching posting counts/dedup logic should be checked against this contract and `tests/testthat/test-k12-posting-identity.R` / `test-opi-reconcile.R`.

**OPI vs. direct scrapes: de-duplicated posting by posting** (`opi_reconcile.R`, matcher in `opi_matcher.R`). K-12 covers 201 directly-scraped districts (of Montana's ~398 nominal districts) plus OPI's statewide feed; HE covers 23 institutions. `mt_district_crosswalk.csv` (NCES CCD, refreshed each run) ties every public district to the registry district whose board covers it, or none; each OPI posting's detail page names its district (`OPI_District`, CCD's naming) and gives the description/school the matcher uses. In the combine step `reconcile_opi_with_direct()` drops an OPI posting at a district we scrape only when `match_opi_postings()` finds the same opening on that district's board (flagging it `Also_On_OPI`); every other OPI posting counts under the registry district and is listed in `mt_discrepancy_report.csv` (many districts post teaching jobs only on OPI). OPI's repeat listings (same district + description) count once; when a board returned nothing, OPI postings over 60 days old aren't used; and it counts OPI postings at districts we don't scrape under their crosswalk `Map_Entity` (adoption candidates, `opi_adoption_candidates.csv`; map rows in `opi_only_districts.csv`, badged "Postings via OPI's statewide board"). The raw archive keeps every OPI row with `OPI_Counted`; `opi_rule_for_archive()` applies the same rule to older archives (the rebuild script and `scripts/reconcile_opi_history.R` use it). `.github/scripts/check_opi_crosscheck.R` puts the QC list and adoption candidates in the drift issue. Any change touching OPI counting should keep `tests/testthat/test-opi-reconcile.R` and `test-opi-matcher.R` (142 hand-labeled real postings; zero wrong-posting matches allowed, misses/false matches capped) passing. `scripts/reconcile_opi_history.R` rebuilds the history under the current rule from the raw archives (rerunnable). `salarymap2.csv`/`salarymap.csv` are the registry-keyed join targets for that narrower scope; several external staffing/salary/finance sources (`MT_CCD_LEA_MAP`, `MT_DLI_DISTRICT_MAP`, `MT_OPI_FINANCE_LEA_MAP`, `MT_IPEDS_UNITID_MAP`) cover only a subset of the 201/23 even within that scope (CCD, SAIPE and OPI finance now reach every registry district the crosswalk ties to CCD) — treat `NA` in those columns as a real, documented coverage gap or source-side suppression, not a bug, per `DATA_COOKBOOK.md`'s "Notes on the data model".

**Elementary/HS district splits are mapped three separate times.** Montana towns often run legally separate elementary and high-school districts sharing one job board (one registry entry, one scrape target) but different external-source naming. `MT_CCD_LEA_MAP` (`ccd_staff_scraper.R`), `MT_DLI_DISTRICT_MAP` (`salary_scrapers.R`), and `MT_SAIPE_DISTRICT_MAP` (`census_saipe_scraper.R`) each hand-map some of this project's combined districts to that source's own elementary/HS/unified naming independently — they are not shared, because each source's naming convention differs slightly from the others. CCD, SAIPE and OPI finance fill every other registry district from `mt_district_crosswalk.csv` (`crosswalk_lea_names()` / `crosswalk_leaids()` in `opi_reconcile.R`; the hand maps win); DLI stays hand-mapped only.

**CI does real work beyond "run tests."** `.github/workflows/weekly-scrape.yml` runs the full `testthat` suite first (aborts before touching real data if red), then the pipeline, then a sanity check (`.github/scripts/sanity_check.R`, refuses to commit if either side of the diff dropped more than half its postings), a schema check (`verify_schema.R`), and a data-quality invariant sweep re-run against the fresh output (`test-weekly-data-quality.R`, blocking), then several non-blocking (`continue-on-error`) monitoring steps: `check_drift.R` (per-source posting-count drift vs. history), `corroborate_drift.R` (live `chromote` render as corroboration before filing a GitHub Issue), `check_salary_drift.R` and `check_census_drift.R` (coverage/plausibility checks against each source's known-fixed or known-partial universe), and `check_pay_coverage.R` (flags a source whose postings still arrive but whose posted pay has gone missing, against its own history in the raw archives, and lists posted amounts `drop_implausible_pay()` blanked), `check_title_quality.R` (titles that aren't job titles -- page text, summaries, a level with no role, pay the Posted Pay column doesn't carry -- and sources whose share of Other jumped against their last 8 weeks), and `check_opi_crosscheck.R` (OPI postings our scrapes missed, scrapes that came back empty, districts to adopt). `check_salary_drift.R` also reports the reference tables behind the pay estimates (OEWS, QCEW, IPEDS staff pay, OPI district counties) whose refresh failed, was rejected by `write_reference_file()`, didn't run, or has gone stale (`reference_table_status()`; see DATA_COOKBOOK.md, "Pay data-quality guards"). The last monitoring step, `check_run_expectations.R`, checks this run's files against `run_expectations.csv`: one row per thing a person expects after a change lands (file, R filter, R measure, min/max, the run dates it applies to; logic in the `edjobs` package). Write expectations for the next run there rather than as a hand-read watch-list; `test-run-expectations.R` validates the file and the pinned `edjobs` version, and failures go in the drift issue. A final step checks whether any monitoring step itself crashed (distinct from "ran fine, found nothing"), since `continue-on-error` alone would hide that distinction. A `guard` job ahead of the scrape skips a *scheduled* run when main already has that day's `Automated weekly data refresh` commit (GitHub starts the cron hours late, after a manual dispatch has pushed); manual dispatches always run, and `concurrency` keeps two runs from overlapping. When changing a scraper or a monitoring script, keep in mind these run against real fixture-backed tests first — see "Fixtures are real captured data" below.

**Likely-broken scrapers are handed to an auto-fix agent (Claude by default), and PRs are checked live.** The drift check's corroboration step (`corroborate_drift.R`) sorts each flagged source into a verdict and writes them to `/tmp/drift_results.csv`. `file_autofix_issues.R` then opens one `scraper-autofix` issue per **`likely_broken`** source and hands it off according to the `AUTOFIX_ENGINE` repo variable (`autofix_engine()`): `claude` (default) dispatches `claude-autofix.yml`, `copilot` assigns it to Copilot via `COPILOT_TOKEN`, and `none` only files it. With `copilot` and a Claude credential in the repo (`CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`), an issue still flagged at a later weekly run, at least 5 days old, with no open Copilot PR carrying changes and no merged fix, goes to `claude-autofix.yml` once (`autofix_escalation_decision()`; a marker comment records the hand-over). Both states run on Copilot with Claude as that fallback since 2026-11-11. `likely_broken` means the live page shows postings the parser missed, e.g. Thompson Falls and Hinsdale after a markup change. Site-side verdicts (`confirmed_broken` HTTP 429/5xx, `looks_genuinely_empty`) are never eligible, because a code change can't fix them. The script opens at most 3 issues per run, and each issue closes on its own once the source recovers. The rolling "Scraper drift check" issue stays the human summary. The logic is pure and tested in `drift_check.R` ("Tier 3" block — drift-alert tier, unrelated to the test-suite tiers below):
- `resolve_scraper_call()` / `run_scraper_call()` map a registry row to its scraper, including `APPTEGY_DISTRICT_SCRAPERS` and chromote scrapers.
- `build_autofix_issue_body()` carries an `<!-- autofix-source: ... -->` marker, and a "What CI saw" section (`gather_autofix_evidence()`): the page text `corroborate_drift.R` rendered in CI, the scraper's fixtures, and a diff of the newest text fixture against that text. The agent's firewalled render can't be trusted (issue #7: blocked Apptegy CDNs → empty page → misdiagnosis). `scripts/repro_scraper.R "<source>"` runs one scraper against its fixture tests and the live site.

`claude-autofix.yml` runs `anthropics/claude-code-action` on an unfirewalled runner with R and Chrome. It follows the `jobs-dash-scraper` skill (`.claude/skills/jobs-dash-scraper/`, vendored from `~/repos/claude-toolkit` via its `sync_to_repos.sh`, so edit it there, not here). Claude only edits the working tree. Then plain workflow steps squash the diff, reject it if it touches anything beyond the scraper files and `tests/testthat/`, re-run the suite, and push or open the PR with `AUTOFIX_PR_TOKEN` (falling back to `COPILOT_TOKEN`), because a PR opened with the Actions token wouldn't trigger `pr-tests.yml`. If Claude decides a human is needed, it comments its report on the issue instead. The issue body carries third-party page text, which is why the model gets no push or `gh` access. The same skill drives local sessions, including discovering and adopting new districts and rechecking declined ones.

`pr-tests.yml` runs the full suite on every PR. On a PR linked to an auto-fix issue, `live_check_autofix.R` re-runs just that scraper against the live site and comments the result, since the agent wrote both the fix and the fixture. The agent's sandbox is set up by `copilot-setup-steps.yml` (shared `.github/actions/setup-r-env`; `weekly-scrape.yml` keeps its own package list because it feeds the Connect manifest — keep the two in sync). Its rules are in `.github/copilot-instructions.md`. The agent runs behind a firewall whose allowlist is kept in `.github/copilot-allowlist.txt`. `test-copilot-allowlist.R` fails when a registry or scraper host isn't covered, so **adding a district means adding its domain there and in repo Settings → Copilot → Internet access**. The `main` ruleset only requests a Copilot review and blocks deletion/force-push. Don't add "require a PR" or status-check rules, because the weekly workflow pushes its data commit straight to `main`.

**The test suite is tiered** (modelled on the LASSO project's `smoke → invariants` layering; see `mt-dashboard-test-suite-expansion` memory). Tier 0: `testthat` unit + fixture tests per source. Tier 1: `test-app-boot-smoke.R` boots the real `app.R` in headless Chrome via `shinytest2`, visits every tab, and asserts no Shiny error banner and that the leaflet/plotly/DT widgets actually render — the browser/JS/htmlwidget path that `test-app-reactives.R`'s `testServer()` structurally can't see (`NOT_CRAN=true` + Chrome required, else it skips). Tier 2: `test-weekly-data-quality.R` is a property sweep over the committed output CSVs — no NaN/Inf, range/sign bounds, referential integrity (Posting_ID uniqueness, salarymap2↔registry, category↔color↔collapse-map), enum coverage, temporal sanity — each assertion naming the bug it guards. Tier 3 (an LLM-as-judge anomaly monitor) is planned, not built.

**Fixtures are real captured data, not synthetic.** `tests/testthat/fixtures/` holds real scraped HTML, real downloaded PDFs, and real API responses per source — tests are written against these rather than hand-built synthetic payloads, so a scraper fix should generally come with an updated or added real fixture, not a synthetic one.

**One credential exists in the whole pipeline.** `census_acs_scraper.R` / `census_saipe_scraper.R` need a free `CENSUS_API_KEY` (Census Data API); every other source is a public, keyless API or plain web page. This key is shared with the sibling Wyoming project's own weekly workflow, which is why this project's schedule is deliberately Tuesdays rather than Wyoming's Friday (avoids both pipelines' Census calls landing at the same time).
